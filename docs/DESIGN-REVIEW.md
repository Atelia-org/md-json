# md-json 设计审视

日期：2026-09-15。当前设计以 [DESIGN.md](DESIGN.md) 为准；本文记录裁决依据，不是第二份格式规范。

## 1. 范围与方法

按用户指定的 [dialectical-simplification 技能](C:/Users/gdtut/.codex/skills/dialectical-simplification/SKILL.md) 完成三位独立审视者的第一轮论证与第二轮交叉质询，主线程独立核对标准、源码和示例后裁决。第二轮已收敛，没有启动第三轮。

- Demand skeptic：质疑没有当前消费者支撑的要求与故障模型。
- Minimal architect：寻找重复概念和更小的可执行结构。
- Semantic defender：构造删减后破坏语义的具体反例。
- 共同输入：初稿全文及其中的需求账本；未向第一轮审视者传递其他审视者结论。审视者没有编辑目标文件，主线程在裁决后统一修订。

证据边界：用户明确授权设计与文档改进；目录此前为空，无类库、测试、已发布格式或可检查的实际消费者。用户提到的内部项目是目标用途，尚非已接入证据。相同草案的多次转述不作为独立证据。

## 2. 收敛后的最小模型

```text
Write(V, P): 按显式路径列表 P 外置字符串，以路径替代原值，写出骨架与正文。
Read(M): 以正文标题为回填清单，检查对应占位值，逐项恢复字符串。
```

三个概念保持不变：JSON 骨架、显式 JSON Pointer 列表、带路径的正文块。无新增引用类型、manifest、策略框架或持久状态。保留 `Read(Write(V,P)) ≡ V`；不承诺检测所有仍形成合法文档的删改。

## 4. 决定性反例与修正

### 4.1 末尾 LF：修正示例，保留公式

初稿示例声明原值无末尾 LF，但闭围栏前多了一行空白。以 `"张三常常吹牛皮。"` 为例，示例里的原始区域实际为 `"张三常常吹牛皮。\n\n"`，减去一个 LF 后仍多一个 LF。

三位审视者和主线程均独立发现此矛盾。现已删除示例多余空行；`originalString + LF + closingFence` 是字符边界的权威规则。空字符串、原末尾 LF、原末尾 CR 等仍按同一公式处理。

### 4.2 错标题与普通字符串

骨架 `{"x":"/x","y":"plain"}` 的 `/x` 正文标题若误写为 `/y`，仅检查路径存在及目标是字符串会覆盖 `plain`。保留 `skeleton[p] == p` 即可拒绝，不需要第二份引用表。

反过来，原始值 `{"x":"/x"}` 配空正文区段必须能保持原值。因此不能全局扫描长得像路径的字符串并自动解引用。完整删除正文块仍可能生成合法文档，是明确保留的边界。

### 4.3 路径解码顺序

`/a~1b` 指向键 `a/b`，不能先解码斜杠再分段。`/~01` 指向键 `~1`，不能反复解码成 `/`。标题先经 JSON 字符串解码，路径随后按 RFC 6901 分段并对 token 单次解码，复用两种标准即可。[RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)

### 4.4 来源修正与明确撤回

Demand skeptic 第一轮建议只对引用位置检查重复键，其余等待 DOM 选择；第二轮在检验“统一唯一键支持域”的论据后明确撤回该建议。最终保留全局唯一键，同时撤回“RFC 强制全树唯一”的归因。

反例 `{"x":"正文","meta":{"a":1,"a":2}}` 中，`/x` 没有路径歧义。使用能保留重复成员的模型也可能完成往返，不能把后续 DOM 可能丢值说成当前已经观察到的失败。现有需求没有要求该模型，故采用更小的唯一键支持域。

初稿“JSON 键或值含围栏字符，所以骨架需要动态围栏”的必要性论证也撤回。严格 JSON 的字符串规则足以支撑固定骨架围栏；原样正文仍必须动态围栏。[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)

### 4.5 源码覆盖

在合法区段之间插入 `[unused]: /url`，它不是空白，也不是 md-json 允许的块。CommonMark 的链接定义不对应普通文档结构元素，因此不能只从可见输出或目标 AST 节点推断“没有额外源码”。[CommonMark 链接定义](https://spec.commonmark.org/0.31.2/#link-reference-definitions)

最小补充是检查已接受源码范围之外的间隙；正文块内部的同样字符完全保留。此结论不等于宣称某个 Markdig 包必然隐藏该节点：选定版本如何保存定义和范围仍需运行探针。

## 5. 验证状态与下一步

本轮完成的是文档验证：

- 用 System.Text.Json 解析示例中的 JSON 骨架。
- 按精确分隔字符公式核对示例两块正文，确认修正后与原值逐字符一致。
- 核对空值、LF、CR、CRLF、连续 LF、NUL 共七个字符算式样例。
- 核对文档内围栏配对、相对链接和行尾空白。

这些检查不构成 md-json 解析器或 Markdig 包的运行验证。没有类库实现，没有 xUnit 结果，没有实际 LLM 关联准确率数据；当前目录也尚未初始化 Git。

没有剩余的产品裁决点。下一步最小技术切片见设计 §8：选定 JSON DOM 和 Markdig 包后，先验证源码定位、CR/NUL、块外内容与数值保真，再实现两个概念接口的往返闭环。不要因本次设计审视自动扩展为实现任务。
